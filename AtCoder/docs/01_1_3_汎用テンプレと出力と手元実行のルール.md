## 1.6 どの形式が来ても同じに書けるテンプレはあるのか

あります。「**標準入力を最初に全部読んで、空白と改行の区別を無くしてしまう**」方法です。

```python
import sys

it = iter(sys.stdin.read().split())     # 入力を「単語の列」にしてしまう
def ni():  return int(next(it))         # 数値を 1 個取る
def ns():  return next(it)              # 文字列を 1 個取る
def nl(k): return [int(next(it)) for _ in range(k)]   # 数値を k 個取る
```

`sys.stdin.read()` は入力全体を 1 つの文字列として読み、`.split()` が
**空白でも改行でも区切って**トークンの列にします。つまり

```
   "5\n1 2 3 4 5\n"   →   ['5', '1', '2', '3', '4', '5']
                              ↑ 改行と空白の区別が消える
```

こうなると、**さっきの 6 パターンが全部同じ書き方になります**。

| | 行ごとに読む書き方 | 一括読みの書き方 |
|---|---|---|
| パターン 1 | `N = int(input())` | `N = ni()` |
| パターン 2 | `A, B = map(int, input().split())` | `A, B = ni(), ni()` |
| パターン 3 | `A = list(map(int, input().split()))` | `A = nl(N)` |
| パターン 4 | `A = [int(input()) for _ in range(N)]` | `A = nl(N)` |
| パターン 5 | `AB = [tuple(map(int, input().split())) for _ in range(N)]` | `AB = [(ni(), ni()) for _ in range(N)]` |
| パターン 6 | `S = [input() for _ in range(H)]` | `S = [ns() for _ in range(H)]` |

**パターン 3 と 4 が完全に同じ `nl(N)` になる**のが、この書き方のいちばん分かりやすい利点です。
「1 行に横に並んでいるか、N 行に縦に並んでいるか」を気にしなくてよくなります。
おまけに `input()` を N 回呼ぶより**速い**ので、10^5 行の入力では実測で差が出ます。

### では、なぜ最初からこれを教えないのか

デメリットが 3 つあるからです。

| 欠点 | 中身 |
|---|---|
| **行の構造が見えなくなる** | 読み間違えても気づきにくい。`ni()` を 1 回余分に呼ぶと以降が全部ズレる |
| **インタラクティブ問題で使えない** | 「こちらが出力すると次の入力が来る」形式の問題では、`read()` が入力の終わりを待ち続けて**止まります**（TLE）。この場合は `input()` を 1 行ずつ使う |
| **問題文と対応させにくい** | 問題文は「1 行目に N、2 行目に A_1 … A_N」と行で書かれている。行ごとに読む書き方のほうが読み合わせしやすい |

現実的な指針はこれです。

```
   競プロを始めたばかり  → §1.4 の 6 パターン（行ごと）で書く。問題文と 1 対 1 に対応して安全
   入力が 10^5 行を超える → §1.6 の一括読み、または input = sys.stdin.readline（§8.1）
   インタラクティブ問題   → 必ず行ごと。一括読みは使わない
```

**折衷案としていちばん使われているのが [§8.1 貼るテンプレ](./01_8_Python落とし穴と提出前チェックリスト.md) の
`input = sys.stdin.readline`** です。書き方は §1.4 のままで速度だけ上がるので、
まずはこれを貼るところから始めるのが安全です。

## 1.7 出力で落とすパターン

| やりがちなミス | 何が起きる | 正しい書き方 |
|---|---|---|
| 「Yes」を `print("YES")` と書く | WA | 問題文の表記を**コピペ**する |
| 複数の答えを 1 行にまとめて出す | WA | 問題文が改行区切りなら 1 個ずつ `print` |
| `print(f"答えは {ans}")` | WA | 余計な文字を出さない。**答えだけ** |
| 小数の答えを `print(x)` で出す | WA のことがある | 誤差の許容が書いてあるか確認 → [§8.4 float の罠](./01_8_Python落とし穴と提出前チェックリスト.md) |
| リストをそのまま `print(A)` | WA（`[1, 2, 3]` と出る） | `print(*A)` でスペース区切り |

`print(*A)` の `*` は**アンパック**といって、リストの中身をバラバラの引数として渡す書き方です。
`A = [1,2,3]` なら `print(1, 2, 3)` と同じになり、`1 2 3` と出力されます。

改行区切りで出したいときは `print('\n'.join(map(str, A)))` が定番です
（`print` を N 回呼ぶより速い。理由は [§8.3 速い書き方](./01_8_Python落とし穴と提出前チェックリスト.md)）。

## 1.8 手元での動かし方と、「試してから提出」はルール上いいのか

### 結論：まったく問題ありません。むしろ推奨されます

**AtCoder のジャッジは、提出されたソースコードを自分の環境で実行するだけ**です。
あなたが手元でそのコードを何回実行したか、どんなファイルを作ったかは一切見ていませんし、
関係もありません。

- サンプル入力を `in.txt` に保存して流し込む → **OK**
- 別ファイル `test.py` を作って、関数だけ切り出して動作確認する → **OK**
- 自分で作った入力（N=1 や最大ケース）で試す → **OK。むしろ WA を減らす最短ルート**
- 総当たりの遅い解法を別ファイルに書いて、速い解法と答えを突き合わせる → **OK**
  （**ストレステスト**と呼ばれる定番の手法です）

```bash
python3 a.py < in.txt     # ファイルから流し込む（直接打つなら python3 a.py、終了は Ctrl-D）
```

`in.txt` に問題文の「入力例 1」をコピペしておき、流し込んで実行する。
これを毎回やるだけで提出前のミスがかなり減ります。

### ただし 1 つだけ注意：提出するコードから外部ファイルを読んではいけない

手元にある `in.txt` は、**ジャッジ環境には存在しません**。

```python
data = open("in.txt").read()     # ✗ 提出すると RE（ファイルが無い）
data = sys.stdin.read()          # ○ 入力は必ず標準入力から
```

デバッグ中に `open(...)` で読むようにしていたら、**提出前に標準入力に戻す**のを忘れないこと。
提出するのは 1 ファイル分のソースコードだけで、`in.txt` や `test.py` は送られません。

### コンテスト中にやっていいこと・ダメなこと

細かい規定は AtCoder の公式ルールページと各コンテストのページに書かれていて、
**改定されることがあります**。ここに書くのは 2026-09-17 時点の一般的な理解なので、
**参加前に必ず公式を確認してください。**

| | 内容 |
|---|---|
| **やっていい** | 手元での実行・デバッグ、**自分が過去に書いたライブラリのコピペ**、アルゴリズムをネットや書籍で調べる、公開されているライブラリの利用、この資料のような解説を読む |
| **やってはいけない** | コンテスト中に他の参加者と問題や解法について相談する、解答を見せ合う・公開する、複数アカウントでの参加 |
| **必ず確認** | **生成 AI の利用**。AtCoder は生成 AI について専用のルールを設けており、コンテストの種類や時期によって可否が変わります。Rated なコンテスト中は制限がかかっていることがあります |

「**自分が過去に書いたライブラリのコピペが許されている**」のは実戦上とても重要です。
だからこそ [§6.6 Union-Find](./01_6_D問題その2_グラフ_BFS_DFS_UnionFind.md) や
[§7.4 mod と逆元](./01_7_D問題その3_数学_約数と素数とmod.md)、
[§8.1 貼るテンプレ](./01_8_Python落とし穴と提出前チェックリスト.md) を
**あらかじめ手元のファイルに用意しておく価値があります**。コンテスト中に 1 から書く必要はありません。

なお、**コンテストが終わったあとの過去問（練習）には、これらの制限はありません**。
順位もレーティングも動かないので、解説を読んでも他人のコードを写経しても自由です。
精進中は気にせず、通らなければすぐ解説を読んでください。

## 1.9 このページのまとめ

- 入力の受け取りは **6 パターンを暗記**。違いは「1 行に何個」×「何行くり返すか」の 2 軸だけ
- パターン 3 で `N` を使わないのは、**1 行目を消費するために読んでいる**から（§1.5）
- **どの形式でも同じに書けるテンプレはある**（§1.6）。ただしインタラクティブ問題では使えない
- 出力は**答えだけ**。`Yes` / `No` は問題文からコピペ
- **手元で実行してから提出するのは完全に OK。** ただし提出コードから外部ファイルを読まない（§1.8）

## 理解度チェック

<details>
<summary><b>Q1.</b> 手元で `data = open("in.txt").read()` と書いてデバッグしていた。そのまま提出するとどうなる？</summary>

**A.** ジャッジ環境に `in.txt` は存在しないので `FileNotFoundError` → **RE**。
手元で試すこと自体はルール上まったく問題ないが、**提出するコードは必ず標準入力から読む**
（`input()` か `sys.stdin`）。提出されるのはソースコード 1 ファイルだけで、
手元のテスト用ファイルは送られない。→ §1.8
</details>

<details>
<summary><b>Q2.</b> コンテスト中に、前のコンテストで自分が書いた Union-Find をコピペして使うのは？</summary>

**A.** **問題ない。** 自分のライブラリの持ち込み・流用は許されている。
だから Union-Find・nCr・入力テンプレなどは**あらかじめ手元に用意しておく**のが正解で、
本番で 1 から書く必要はない。一方、**コンテスト中に他の参加者と問題や解法について
相談すること**は禁止。生成 AI の利用は専用ルールがあるので公式を確認する。→ §1.8
</details>

<details>
<summary><b>Q3.</b> `it = iter(sys.stdin.read().split())` の一括読みテンプレを、絶対に使ってはいけないのはどんな問題？</summary>

**A.** **インタラクティブ（対話型）問題**。こちらが出力してから次の入力が来る形式なので、
`read()` が「入力の終わり」を待ち続けて永久に返ってこない（TLE になる）。
この場合は `input()` で 1 行ずつ読み、`print` のあとに必要なら `sys.stdout.flush()` する。→ §1.6
</details>

<details>
<summary><b>Q4.</b> 答えのリスト `ans`（10 万要素）を 1 行ずつ出したい。`for x in ans: print(x)` で大丈夫？</summary>

**A.** 正しくは出るが**遅い**。`print` の呼び出し 1 回ごとにコストがかかるので、
10 万回呼ぶと TLE の一因になる。`print('\n'.join(map(str, ans)))` と
**1 回にまとめて出す**のが定番。なおスペース区切りなら `print(*ans)`。→ §1.7 / §8.3
</details>
