2.1git init は「フォルダを 1 個作るだけ」のコマンド

$ mkdir myapp && cd myapp
$ git init
Initialized empty Git repository in .../lab/myapp/.git/

やっていることは、カレントディレクトリに .git を作り、雛形を展開することだけです。ネットワークにも、親ディレクトリにも、既存ファイルにも一切触りません。作業ツリーのファイルは 1 個も追跡対象になりません（git status で確認できます）。

何度実行しても壊れない

$ git init .../lab/t2
Reinitialized existing Git repository in .../lab/t2/.git/

Initialized ではなく Reinitialized になります。既存の .git があるときは、足りない雛形を補うだけで、objects も refs も config も消しません。「うっかり 2 回 git init した」で履歴が飛ぶことはないので安心してください。

ただし例外があります。git init --initial-branch=xxx を既存リポジトリで実行するとHEAD が書き換わります。コミット済みのリポジトリでは付けないでください。

GitWeb 用の 1 行説明

.git/index はまだ存在しません。

$ ls -la .git/index
ls: .git/index: No such file or directory

これが「まだ一度も git add していない」ことの機械的な判定条件です。

2.3.git/HEAD — 存在しないブランチを指している

$ cat .git/HEAD
ref: refs/heads/main
$ wc -c .git/HEAD
      21 .git/HEAD

21 バイトのテキスト 1 行です。ref: で始まるものを symbolic ref と呼び、「refs/heads/main というファイルを見に行け」という転送指示になります。

HEAD にはハッシュが入っていない点に注意してください。40 桁のハッシュを直接持つのはブランチ側（refs/heads/main、41 バイト）です。HEAD がハッシュを直接持つのは detached HEAD のときだけで、それが「detached（切り離された）」と呼ばれる理由です（01_5 §5.5）。

ここが git init 最大の引っかかりどころ

.git/refs/heads/main はまだ存在しません（§2.2 の find 出力を見てください）。つまり HEAD は壊れたリンクを指している状態です。これは異常ではなく、正常な初期状態です。

Git はこれを「unborn branch（まだ生まれていないブランチ）」として特別扱いします。

$ git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

$ git branch
（何も出力されない）

$ git symbolic-ref HEAD
refs/heads/main

$ git rev-parse HEAD
fatal: ambiguous argument 'HEAD': unknown revision or path not in the working tree.

git status は「On branch main」と言うのに git branch には 1 行も出ない。この食い違いは、git branch が refs/heads/ のファイルを列挙しているのに対し、git status は HEAD のテキストを読んでいるためです。実装の違いがそのまま出ています。

refs/heads/main は、最初の git commit のときに初めて作られます（§4.3）。

ブランチ名を変えたいなら init 時に指定できます。

$ git init --initial-branch=develop .../lab/t2
Initialized empty Git repository in .../lab/t2/.git/
$ cat .git/HEAD
ref: refs/heads/develop

既定値は init.defaultBranch 設定で決まります。設定していないと Git が警告を出します。

$ git config --list --show-scope | head -4
unknown	credential.helper=osxkeychain
unknown	init.defaultbranch=main
global	user.name=...
global	user.email=...

unknown スコープは、Xcode Command Line Tools 版 Git が持っているシステム設定です（/Applications/Xcode.app/... 配下など、git config --show-origin で実体が見えます）。

2.4.git/config — 1 行ずつ意味がある

myapp/.git/config（git init 直後の実物）
[core]
	repositoryformatversion = 0
	filemode = true
	bare = false
	logallrefupdates = true
	ignorecase = true
	precomposeunicode = true
キー意味変えるとどうなるか
repositoryformatversion.git のフォーマット世代。0 が通常、1 は拡張機能あり手で触らない。SHA-256 リポジトリなどで 1 になる
filemode実行ビット（100755）の変化を差分として扱うかfalse にすると chmod が無視される。Windows 共有や Docker マウントで true のままだと全ファイルが変更扱いになる事故が起きる
bare作業ツリーを持たないか§2.8
logallrefupdatesreflog（.git/logs/）を書くかfalse にすると git reflog で復旧できなくなる。絶対に切らない
ignorecaseファイル名の大小を区別しないファイルシステムかmacOS / Windows で true。README.md → Readme.md のリネームが認識されない原因
precomposeunicodemacOS の NFD 正規化（濁点分解）を NFC に戻すかmacOS 専用。false だと「が」が「か + ゛」として記録され、Linux 側で別ファイルに見える

ignorecase と precomposeunicode は環境を見て自動で決まった値です。Linux で git init すればどちらも出てきません。ここが .git/config の面白いところで、リポジトリを作った環境の性質が固定値として焼き付きます。

設定は 4 段重ねで、下が勝つ

systemGit が入っている場所。全ユーザー共通
global~/.gitconfig。あなた個人
local.git/config。このリポジトリだけ← git init が作るのはここ
worktree.git/config.worktree。使うことは稀
下の段ほど強い（上書きする）

どこで決まっているか分からなくなったら --show-origin で追えます。

$ git config --show-origin --get core.ignorecase
file:.git/config	true

なお user.name / user.email は git init では書かれません。global にも無いと最初の git commit で止まります。

理解度チェック（前編）

Q1. git init 直後、git status は "On branch main" と言うのに git branch は何も出さない。どちらが正しい？

A. どちらも正しい。.git/HEAD には ref: refs/heads/main と書かれている（status はこれを読む）が、.git/refs/heads/main というファイルはまだ存在しない（branch はこれを列挙する）。最初の git commit で実体が作られる。 → §2.3

Q2. Docker でマウントしたリポジトリで、何も触っていないのに全ファイルが変更扱いになった。どこを見る？

A. .git/config の core.filemode。ホストとコンテナで実行ビットの見え方が違うと、100644 ↔ 100755 の変化として全ファイルが差分になる。git config core.filemode false で止まる。 → §2.4

Q3. 既存のリポジトリでうっかり git init をもう一度実行してしまった。履歴は消えた？

A. 消えない。Reinitialized existing Git repository と出て、足りない雛形を補うだけ。ただし --initial-branch=xxx を付けると HEAD が書き換わるので、コミット済みリポジトリでは付けないこと。 → §2.1
