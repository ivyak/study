## 9.2 壊したときの復旧手順

**大前提：`.git/objects` は追記のみで、オブジェクトは消えません。**
「消えた」と見えるものは、ほぼすべて**名前（ref）が外れただけ**です。順に試してください。

### ① 直前の操作を取り消す — `ORIG_HEAD`

```bash
git reset --hard ORIG_HEAD
```

`merge` `rebase` `reset` `pull` の直前の位置が入っています。**やらかした直後ならこれで戻ります。**
ただし 1 つ前しか覚えていないので、次の破壊的操作をすると上書きされます。

### ② もっと前に戻す — reflog

```bash
git reflog                     # .git/logs/HEAD を整形表示
git reset --hard HEAD@{5}      # 5 つ前の位置へ
git branch recover 90d3702     # 消したブランチを復活（§5.6）
```

`git reflog` が読むのは `.git/logs/HEAD` です。ブランチ個別の reflog は
`git reflog show <ブランチ名>`。ただし `git branch -D` するとそのブランチの分は消えます。

保持期間の既定は、到達可能なもの 90 日・到達不能なもの 30 日です。

### ③ reflog にも無い — `fsck`

```bash
git fsck --lost-found
```

どの ref からも到達できないオブジェクト（dangling commit / blob）を列挙します。
`git add` はしたがコミットしていない内容も、blob として拾えます（[§3.1](./01_4_add-commit_indexとオブジェクトの増え方.md)）。

### ④ マージ・リベースの途中でやめる

```bash
git merge --abort     # .git/MERGE_HEAD を消して ORIG_HEAD の状態へ
git rebase --abort
git cherry-pick --abort
```

**やってはいけないこと**：`.git/MERGE_HEAD` などを手で `rm` すること。
index の 3 段（[§8.4](./01_8_git-pull_fetchとmergeの合わせ技.md)）が残ったままになり、状態が矛盾します。

## 9.3 やりたいこと → 触る場所

| やりたいこと | コマンド | 書き換わる `.git` のファイル |
|---|---|---|
| ブランチを作る | `git branch x` | `refs/heads/x` を新規作成（41 バイト） |
| ブランチを移る | `git switch x` | `HEAD`、`index`、作業ツリー |
| コミットする | `git commit` | `objects/**`、`HEAD` が指す `refs/heads/*`、`logs/**` |
| リモートを登録する | `git remote add` | `config` のみ（通信しない） |
| リモートの最新を見る | `git fetch` | `objects/**`、`refs/remotes/**`、`FETCH_HEAD` |
| 取り込む | `git merge` / `pull` | 上記 + `refs/heads/*`、`index`、作業ツリー、`ORIG_HEAD` |
| 直前のコミットを直す | `git commit --amend` | 新しい commit を作り `refs/heads/*` を向け直す |
| 上流を設定する | `git push -u` / `branch -u` | `config` の `[branch "x"]` |
| リモートで消えた枝を掃除 | `git fetch --prune` | `refs/remotes/**` のみ（`refs/heads` は触らない） |

## 9.4 `.git` がディレクトリではなくファイルのとき

`git worktree` とサブモジュールでは、`.git` が**ファイル**になります。

```console
$ git worktree add ../wt-signin feature/signin
Preparing worktree (checking out 'feature/signin')
HEAD is now at 90d3702 ログイン画面を追加

$ ls -la ../wt-signin/.git
-rw-r--r--@ 1 akito_inoue  wheel  156 Sep 17 13:20 ../wt-signin/.git

$ cat ../wt-signin/.git
gitdir: .../lab/myapp/.git/worktrees/wt-signin
```

本体側には、その作業ツリー専用の状態が置かれます。

```console
$ find .git/worktrees | sort
.git/worktrees/wt-signin
.git/worktrees/wt-signin/HEAD
.git/worktrees/wt-signin/ORIG_HEAD
.git/worktrees/wt-signin/commondir
.git/worktrees/wt-signin/gitdir
.git/worktrees/wt-signin/index
.git/worktrees/wt-signin/logs
.git/worktrees/wt-signin/refs

$ cat .git/worktrees/wt-signin/HEAD
ref: refs/heads/feature/signin
```

**`HEAD` と `index` だけが作業ツリーごとに分かれ、`objects` と `refs` は共有**されています。
だから同じブランチを 2 つの作業ツリーで同時にチェックアウトすることはできません
（`refs/heads/x` が 1 つしか無いのに、2 つの `HEAD` から指されて矛盾するため）。

同じリポジトリで並行作業したいときは、clone をもう 1 つ作るより軽量です。
オブジェクトを共有するので、ディスク消費もほぼ増えません。

## 9.5 `git gc` のあと `refs/heads/main` が消えた

壊れていません。`git gc` は refs をテキスト 1 枚にまとめます。

```console
$ find .git/refs -type f | sort          # gc 前
.git/refs/heads/feature/signin
.git/refs/heads/main
.git/refs/remotes/origin/HEAD
.git/refs/remotes/origin/main

$ git gc --quiet

$ find .git/refs -type f | sort          # gc 後
.git/refs/remotes/origin/HEAD

$ cat .git/packed-refs
# pack-refs with: peeled fully-peeled sorted
90d3702af1f82bd83330bf8f5594b278b4504d58 refs/heads/feature/signin
47c402e76780186c8f4ddd926f92b7ebae98b9c7 refs/heads/main
14cdc052dfae223a470286ef8f8e3eca04b304b0 refs/remotes/origin/main
```

Git は ref を探すとき、まず `refs/` 以下のファイルを見て、無ければ `packed-refs` を見ます。
数千ブランチあるリポジトリで `refs/` に数千ファイルを置くのは効率が悪いので、まとめてあるわけです。
**`git rev-parse main` が値を返せば健全です。**

オブジェクト側も同時にパックされます。

```console
$ find .git/objects -type f | sort
.git/objects/info/commit-graph
.git/objects/pack/pack-31162f40....idx
.git/objects/pack/pack-31162f40....pack
...
```

ここで [01_1 §1.1](./01_1_Gitの世界観_4種類のオブジェクト.md) の宿題
（スナップショット方式なのに容量が膨らまない理由）が回収できます。パックの中では delta 圧縮が効いています。

```console
$ git verify-pack -v .git/objects/pack/pack-31162f40....idx
ef7701ff00345f0f0347d776977a2d5ad7b4607e tree   186 163 2430
8f7c3de4b6025b343a7f95bc479cfb53e67a711c tree   7 18 2593 1 ef7701ff00345f0f0347d776977a2d5ad7b4607e
bfb0383a57db9475151cb0df158d2fe44c4922cd tree   5 15 2628 2 8f7c3de4b6025b343a7f95bc479cfb53e67a711c
...
chain length = 1: 4 objects
chain length = 2: 1 object
```

末尾にハッシュがある行が「右のオブジェクトからの差分として格納した」という意味で、
手前の数字が delta チェーンの深さです。186 バイトの tree を基準に、以降は 7 バイト・5 バイトで済んでいます。

**この最適化は論理モデルに影響しません。** `git cat-file -p` はパックの中からでも完全な中身を返します。

## 9.6 `.git` を覗くコマンド集

```bash
# 今いる場所
cat .git/HEAD                    # ref: refs/heads/... か 40 桁ハッシュか
git symbolic-ref HEAD            # detached なら失敗する
git rev-parse HEAD               # 今のコミット

# オブジェクトを読む
git cat-file -t <hash>           # 種類
git cat-file -p <hash>           # 中身
git cat-file -p HEAD^{tree}      # ルートの tree
git cat-file -p HEAD^{tree}:src  # サブディレクトリの tree

# ステージ
git ls-files -s                  # index の中身
git ls-files -u                  # 未解決（コンフリクト中だけ出る）
git ls-files --debug             # index が持つ stat 情報

# ref
git show-ref                     # refs/ と packed-refs を合わせた一覧
git rev-parse --symbolic-full-name main       # → refs/heads/main
git rev-parse --symbolic-full-name origin/main # → refs/remotes/origin/main

# 履歴と差分
git reflog                       # .git/logs/HEAD
git log --oneline main..origin/main   # 取り込んでいないコミット
git log --oneline --graph --all       # 枝分かれの形
```

`^{tree}` の `^{...}` は「その種類になるまで剥がす」記法で、タグ → コミット → tree と自動でたどります。

## 理解度チェック

<details>
<summary><b>Q1.</b> <code>git rebase</code> で履歴を壊した。最初に打つコマンドは？</summary>

**A.** `git reset --hard ORIG_HEAD`。`rebase` は開始前の HEAD を `.git/ORIG_HEAD` に保存する。
これで戻らなければ `git reflog` から `rebase (start)` の 1 つ前を探す。 → §9.2
</details>

<details>
<summary><b>Q2.</b> 同じブランチを 2 つの worktree で同時に開けないのはなぜ？</summary>

**A.** `HEAD` と `index` は worktree ごとに分かれるが、`refs/heads/x` は 1 つしかない。
2 つの `HEAD` から同じ ref を指すと、どちらのコミットで ref を進めるかが決まらず矛盾する。 → §9.4
</details>

<details>
<summary><b>Q3.</b> コンフリクトが面倒になった。<code>rm .git/MERGE_HEAD</code> で抜けてよい？</summary>

**A.** だめ。`index` に 3 段のエントリが残り、`MERGE_MSG` なども取り残されて状態が矛盾する。
`git merge --abort` を使う。これは `ORIG_HEAD` を使って index と作業ツリーごと戻す。 → §9.2 §8.4
</details>
