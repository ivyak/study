基礎A｜8バイトの数が、リストでは約32バイト以上になる理由

まず、次の2×2行列を考える。画面上では数字が4個並んでいるだけに見えるが、Pythonのリストでは「行列全体を入れるリスト」「各行を入れる2個のリスト」「4個の数値」という階層になっている。

小さい行列をリストで表す

A = [[1.0, 2.0],
     [3.0, 4.0]]

A[0]     # 1行目を入れるリスト [1.0, 2.0]
A[0][1]  # 1行目・2列目の値 2.0
外側のリスト A→各行のリスト→各 float オブジェクト

「64ビットの浮動小数点数は8バイト」は、数値の中身を64ビットで表すという意味である。ここでの64ビットは数値形式の幅であり、OSやCPUが64ビットであることとは別の話。NumPyの float64 配列なら、連続したデータ領域に1要素8バイトずつ並ぶ。一方、64ビット版CPythonの通常の float は、数値の中身に加えて型や参照数を管理する領域を持つ独立したオブジェクトで、この環境では1個24バイトだった。これはCPythonの実装に依存し、Pythonの仕様で常に24バイトと決まっているわけではない。

ここでいうオブジェクトは、値に「これは float である」という型の情報などを付けて管理する単位。参照は、値が置かれている場所を指す印と考えればよい。リストは数値の中身を直接並べるのではなく、その参照を並べる。64ビット環境では参照1個の場所がおおむね8バイト。したがって、ランダムに生成した別々の float をリストへ入れると、要素1個につき 24 + 8 ≈ 32 バイトが目安となる。リスト自体の管理領域も別に必要だ。

800次では要素が 800 × 800 = 640,000 個ある。数値データだけなら 640,000 × 8 = 5,120,000 バイト。Pythonリストでは、数値オブジェクトと参照だけで 640,000 × (24 + 8) = 20,480,000 バイトになり、行リストなどの分がさらに加わる。小さな差が数十万回積み重なるため、行列では無視できなくなる。

入れ方1要素の主な内訳800×800行列1個の目安
NumPy float64数値データ8バイト5,120,000バイト（5.12 MB）＋配列本体
Pythonのリスト内の floatfloat オブジェクト約24バイト＋参照約8バイト実測約20,915,736バイト（20.9 MB）

sys.getsizeof(A) は外側のリストだけを数え、行リストと float の大きさは含まない。次のコードは各層の大きさを足す。この例では各計算で新しい float を作るので、同じオブジェクトを重複して足す問題はない。一般には同じオブジェクトを複数箇所で参照する場合もあるため、この方法が常に正確な「深いサイズ」になるわけではない。

この環境での大きさの確認方法

import sys
import numpy as np

print(sys.getsizeof(0.0))  # 24: CPythonのfloatオブジェクト
A = [[0.1 * (i + j) for j in range(800)] for i in range(800)]
deep_bytes = (sys.getsizeof(A)
              + sum(sys.getsizeof(row)
                    + sum(sys.getsizeof(value) for value in row)
                    for row in A))
print(deep_bytes)             # リスト、行、要素を合算
print(np.asarray(A).nbytes)   # 数値データ領域だけ

同じ800次の行列を100個保持すると、Pythonリスト側は約2.09 GBに達する。さらに100個をまとめてNumPy配列へ変換すると、別の数値データ領域だけで約512 MBが加わる。np.asarray(A) は、元が入れ子のPythonリストなら配列用データを新たに作る。一方、すでにNumPy配列ならコピーを作らずに済む場合もある。配列に変換しても、変数 A_list が元のリストを指している間は元の行列も残る。だから100個を同時に持たず、1個ずつ計算する。

基礎B｜リスト内包表記はどこまで速くするか

内包表記とは、[式 for ...] という形でリストを作る書き方である。たとえば [i * i for i in range(3)] は [0, 1, 4] を作る。「i を0、1、2と変え、そのたびに i * i を結果へ入れる」と読める。行列では、この書き方を二重に使う。

n=2なら、内側の式が2行分実行される

A = [[random.random() for _ in range(2)]
     for _ in range(2)]
# 外側: 行を2個作る
# 内側: 各行の値を2個作る
# 合計: random.random() を2×2=4回呼ぶ

_ は「繰り返す回数だけが必要で、ループ変数の値は使わない」という慣習的な名前。内包表記でも通常の for と append でも、作る行と数値の個数は同じである。次の二つはどちらも random.random() を n² 回呼ぶ。

二重forとappend

A = []
for _ in range(n):
    row = []
    for _ in range(n):
        row.append(random.random())
    A.append(row)

リスト内包表記

A = [
    [random.random() for _ in range(n)]
    for _ in range(n)
]

この環境の400次の行列生成では、前者が約5.45 ms、後者が約4.67 msだった。差は約0.78 msで、内包表記の方がこの測定では約14%短かった。ループで append を呼ぶ処理などが減るためで、乱数を作る回数は変わらない。両方とも160,000個のPythonの float を作り、メモリもほぼ同じ。Pythonや処理内容が変われば差も変わる。

この課題で重要なのは、短く書けても、必要な計算の回数までは減らないこと。修正前の残差計算では、Ax 全体を計算する関数を内包表記の中で400回呼んでいた。Ax 1回には400×400回ほどの掛け算と足し算が必要なので、約160,000回の仕事を400回繰り返す。Ax を先に1回だけ計算して保存すれば、式が少し長くなっても仕事量を大幅に減らせる。

内包表記はPythonのループを短く書く方法。NumPyの配列演算は、多数の数値をまとめて処理する別の実装方法。内包表記に書き換えるだけで、消去法の三重ループが自動でNumPyの高速な処理に変わるわけではない。

基礎C｜何に何ミリ秒かかるか

1 ms（ミリ秒）は0.001秒。1000 msが1秒である。表の「約703 ms」は、400次の行列1個を消去法で解く一連の処理に約0.703秒かかった、という意味。100個なら単純計算で約70秒になる。ただし実際の実行では行列生成などの時間も加わる。

「足し算1回は何ms」という値は小さすぎて、時間を測る関数そのものの呼び出しや周囲のPython処理に埋もれる。そこで、行列を1個作る・解く・残差を出す、という区切りのよい処理を1回として測る。次の値は400次の1行列について、処理ごとに独立に繰り返し測った中央値である。

処理の単位1回あたり何をしているか
行列1個の生成（内包表記）約4.67 ms160,000個の乱数と float を生成
行列1個の生成（append）約5.45 ms同じ個数の生成を明示的な二重ループで実行
PythonリストからNumPy配列への変換約2.66 ms160,000個の値を読み、連続領域にコピー
拡大行列の作成約1.26 ms各行をコピーし、右辺の値を追加
前進消去約676 msピボット選択と行更新。純Pythonの三重ループが中心
後退代入約3.41 ms上三角行列から解を求める
消去法全体約703 ms拡大行列、前進消去、後退代入を含む
行列ベクトル積 Ax約5.08 ms400個の内積を計算
修正後の残差ノルム約5.01 msAxを1回作って最大絶対値を計算
修正前の残差ノルム約2,043 msAxを400回作り直す
np.linalg.solve約1.41 ms数値計算ライブラリで基準解を求める

表の中央を見ると、消去法全体の約703 msのうち、前進消去だけで約676 msかかる。このため、消去法の中を速くするなら、まず前進消去の行更新を調べる。さらに修正前の残差計算は約2,043 ms、つまり約2秒もかかっていた。消去法より長いので、先に直す価値が高い。

たとえば400次の1試行で、古い実装は消去法を2回（約703 ms×2）と残差計算を1回（約2,043 ms）行っていた。これだけで概算約3.45秒。修正後は消去法1回と残差1回で約0.71秒になる。これは表の独立測定値からの見積もりで、実際の1試行の総時間を測った値ではない。

np.linalg.solve はライブラリ内部で最適化された処理を使い、ここでは比較用の解を作る。自作の消去法と同じ条件の速度競争と読むべきではない。各値は別々に測った中央値なので、表の行を足して正確な総実行時間にはできない。

「行列1個を解く時間」を測る区間

import time

start = time.perf_counter()             # 開始時刻（秒）
x = utils_math.Gaussian_elimination(A, b)
elapsed_ms = (time.perf_counter() - start) * 1000
print(f"消去法1回: {elapsed_ms:.1f} ms")

測りたい処理を開始時刻と終了時刻で挟む。perf_counter() の差は秒なので、ミリ秒で表示するときは1000を掛ける。この例では行列生成やNumPyの基準解を時刻の間に入れていないため、消去法そのものの所要時間を読める。

測定条件：CPython 3.12.3、NumPy 2.5.3、400×400のランダム行列、OPENBLAS_NUM_THREADS=1。timeit.repeat の中央値を主に使用し、前進消去の内訳は3回の中央値。実行環境、乱数、CPU負荷で数値は変わる。前節までの単発測定と値が少し違うのもそのためである。

基礎D｜Pythonで時間を減らすときの順序

ここで n は行列の縦横の長さ。計算量とは、n を大きくしたときに処理回数がどのくらい増えるかを表す目安である。1本のループなら約 n 回、二重ループなら約 n² 回、三重ループなら約 n³ 回になる。400次から800次へ2倍にすると、n² は約4倍、n³ は約8倍になる。実時間はメモリや実装の影響も受けるので、必ずしもぴったり4倍・8倍にはならない。

処理回数の型400次800次典型例
n400800結果の各成分を1回ずつ見る
n²160,000640,000行列の全要素を見る、Ax を1回作る
n³64,000,000512,000,000密行列の消去法のおおよその増え方、Ax を各成分ごとに作り直す

下の順序は「高速な文法を探す」前に確認すること。短く書くより先に、同じ大きな仕事を何度行っているかを見る。

  1. 何の時間を知りたいか決める。「消去法そのものの速さ」を調べるなら、その関数の前後だけを測る。「プログラムが終わるまでの待ち時間」を知りたいなら、行列生成や描画を含む全体も別に測る。二つを混ぜると、どこが遅いか分からない。
  2. 同じ答えを作り直していないか見る。すでに求めた解 x を捨ててもう一度消去法を呼ぶ、すでに求めた Ax を作り直す、といった箇所を探す。計算結果を変数に置き、必要な場所で再利用する。
  3. 繰り返しの内側を確認する。「100個の行列」×「各行列について400行」×「各行で400成分」のように掛け算で考える。内側で高価な関数を呼ぶと、その費用も全部の回数だけ増える。
  4. 大きいデータを必要な間だけ持つ。今回なら1個の行列を作って解き、その残差・誤差・時間を保存したら次へ進む。行列100個を同時に保持する必要はない。これは主にメモリを減らす工夫だが、メモリ不足による極端な遅さも避けられる。
  5. それでも遅い部分だけ実装を変える。表では前進消去の行更新が長い。そこで、消去法の手順は自分で書いたまま、行の数値計算をNumPy配列にまとめて任せる方法を考える。すべてを一度に書き換えず、同じ結果になるか残差で確かめる。

短い処理は1回の計測値が不安定なので、timeit.repeat で何回か測って中央値を見る。下の例では行列生成を5回ずつ、5組測る。得られる5個の時間はそれぞれ「5回分の秒数」なので、中央値を5で割って1回分にし、1000倍してmsに直す。

短い処理を繰り返して測る例（section2 で実行）

import statistics
import timeit
import utils_math

times = timeit.repeat(
    lambda: utils_math.make_square_matrix(400),
    number=5, repeat=5,
)
ms_per_matrix = statistics.median(times) / 5 * 1000
print(f"{ms_per_matrix:.2f} ms / 行列1個")

比較するときは入力サイズとデータの種類をそろえる。初回だけのライブラリ初期化や描画準備を除き、必要なら事前に一度動かしてから測る。処理別の時間分布を探す道具として cProfile もあるが、道具を使うこと自体に時間がかかるため、最後は perf_counter() で実行時間を確認する。

1｜まず、どこに時間がかかるか

現在の Gaussian_elimination はPythonのリストを用い、前進消去を三重ループで進める。計算量はおおむね次数 n の3乗に比例する。実測では1行列あたり次の時間だった。

0.012秒100次を1個解く時間
0.088秒200次を1個解く時間
0.813秒400次を1個解く時間
7.36秒800次を1個解く時間

800次を100回解くだけで約12分。以前のコードは同じ問題を2回解いていたので、その部分だけで約24分になる。これはこの環境での単発測定からの概算であり、全400試行を通した実測値ではない。

NumPyで行単位の演算を使う自作の消去法を試作したところ、800次1個で約0.47秒だった。アルゴリズムを消去法のまま保ち、要素ごとの反復処理をNumPy側へ移すと改善できる。ただし以下の修正だけでも重複計算とメモリ消費を大きく減らせる。

2｜残差で Ax 全体を毎回作っていた

残差ノルムは max_i |(Ax)_i - b_i|。matrix_vector_product(A, x) は Ax の全成分を計算してリストで返す。修正前は、そのリストから1成分を取り出す処理を n 回繰り返していた。

修正前 · utils_math.py

def residual_norm(A, x, b):
    return infinity_norm([
        matrix_vector_product(A, x)[i] - b[i]
        for i in range(len(b))
    ])

修正後 · Axを一度だけ計算

def residual_norm(A, x, b):
    Ax = matrix_vector_product(A, x)
    return infinity_norm([
        Ax[i] - b[i] for i in range(len(b))
    ])

400次なら、修正前は400成分の Ax を400回作る。行列ベクトル積は約 n² 回の演算なので、残差全体は約 n³ 回。修正後は Ax が1回で済み、約 n² 回になる。求める値は同じである。

次数修正前の残差計算修正後の残差計算
100約0.041秒約0.00037秒
200約0.259秒約0.00139秒
400約2.33秒約0.00577秒

上表はこの環境で各次数1個のランダム行列を使った測定。現在の実装を開く。

3｜計測後に同じ消去法を再実行していた

修正前の get_execution_time は処理時間だけを返すため、後で解 x を得る目的でもう一度消去法を呼んでいた。時間を測る際に得た解をそのまま使えば、各行列について消去法は1回で済む。

修正前 · kadai1_1.py

execution_times = [

]
x_list = [
    Gaussian_elimination(A_list[j], b_list[j])

修正後 · 1回の結果と時間を保存

start = time.perf_counter()
x = utils_math.Gaussian_elimination(A, b)
elapsed = time.perf_counter() - start

times.append(elapsed)
# この x を残差と相対誤差の計算に使う

perf_counter() の差には消去法だけを含める。行列の生成、NumPyによる基準解、残差計算、描画は測定区間の外に置くと、各次数の計算時間を比較しやすい。

4｜100個の行列を一度に持っていた

800次の行列には 800 × 800 = 640,000 個の数が入る。Pythonの浮動小数点数とリスト内の参照を合わせて、1行列あたり概算約20MB、100個で約2GBになる。さらにNumPy配列へ100個まとめてコピーすると、倍精度の要素だけで 100 × 800 × 800 × 8 = 512,000,000 バイト、約512MBが加わる。

修正前 · 100個とコピーを保持

A_list = [
    utils_math.make_square_matrix(n)
    for _ in range(100)
]
b_list = [utils_math.make_vector(n)
          for _ in range(100)]
A_list_true = np.array(A_list)
b_list_true = np.array(b_list)

修正後 · 1個ずつ処理

residuals, errors, times = [], [], []
for _ in range(100):
    A = utils_math.make_square_matrix(n)
    b = utils_math.make_vector(n)
    # A, b を解き、3つの数値を追加する
    # 次の反復では前の A, b は不要

3つの結果リストはそれぞれ100個の数値だけなので、行列100個と比べてごく小さい。基準解を作る np.asarray(A) は、その試行で必要な時だけ行えばよい。次の試行でも同じ行列を参照し続けるリストがなければ、古い行列は回収できる。

上の容量は64ビット環境における概算。Python実装や一時配列により実際のピーク使用量は変わる。

5｜各次数のグラフが同じ位置に重なっていた

最初の描画コードは外側の n のループが進んでも、毎回 subplot(4, 3, 1)、2、3 を使っていた。100次だけが描画されるわけではなく、4種類の曲線が最初の3枠に重なる。また、plt.plot(n, 値) の形で1点だけ描く場合は、線を結ぶ相手がなく、標準設定では点が見えにくい。

修正前 · subplotの番号が固定

for n in [100, 200, 400, 800]:
    # 100回分の結果を計算
    plt.subplot(4, 3, 1)
    plt.plot(residuals)
    plt.subplot(4, 3, 2)
    plt.plot(errors)
    plt.subplot(4, 3, 3)
    plt.plot(times)

修正後 · nごとに1行を使う

for row, n in enumerate([100, 200, 400, 800]):
    # 100回分の結果を計算
    for col, (values, title) in enumerate([
        (residuals, "残差ノルム"),
        (errors, "相対誤差"),
        (times, "計算時間"),
    ]):
        ax = plt.subplot(4, 3, row * 3 + col + 1)
        ax.plot(range(1, 101), values)
        ax.set_title(f"n={n}: {title}")

途中で for row, n in enumerate(...) を元の for n in ... の内側へ追加した状態もあった。そのままでは各次数の結果を4行すべてに描いてしまう。enumerate を外側のループそのものに使い、100回の計算後に描画するのが正しい。

row * 3 + col + 1 は、100次を1〜3枠、200次を4〜6枠、400次を7〜9枠、800次を10〜12枠に割り当てる。横軸は次数ではなく、同じ次数で行った試行番号1〜100である。次数ごとの代表値を1枚の図で比較したい場合は、100回の平均または中央値を別に集計して描く。

6｜課題1の処理をまとめた完成例

以下は、上の4点を一つにまとめた kadai1_1.py の例である。utils_math.py 側では、2節の修正版 residual_norm を使う。現在のソースも同じ処理順で、描画する行を外側のループで決めている。

修正後の全体例 · kadai1_1.py

import time
import numpy as np
import matplotlib.pyplot as plt
import utils_math

sizes = [100, 200, 400, 800]
fig, axes = plt.subplots(4, 3, figsize=(14, 12))

for row, n in enumerate(sizes):
    residuals = []
    errors = []
    times = []

    for _ in range(100):
        A = utils_math.make_square_matrix(n)
        b = utils_math.make_vector(n)

        start = time.perf_counter()
        x = utils_math.Gaussian_elimination(A, b)
        times.append(time.perf_counter() - start)

        x_true = np.linalg.solve(np.asarray(A), np.asarray(b))
        residuals.append(utils_math.residual_norm(A, x, b))
        errors.append(utils_math.relative_error(x_true, x))

    for col, (values, title) in enumerate([
        (residuals, "残差ノルム"),
        (errors, "相対誤差"),
        (times, "計算時間 [s]"),
    ]):
        ax = axes[row, col]
        ax.plot(range(1, 101), values, marker=".", markersize=3)
        ax.set_title(f"n = {n}｜{title}")
        ax.set_xlabel("試行番号")
        ax.grid(alpha=0.25)

fig.tight_layout()
plt.show()

相対誤差関数は relative_error(x_true, x_approx) の順で受け取るため、NumPyの基準解 x_true を第1引数にする。教材は「真の解は不明」として数値計算パッケージの結果を基準にするよう指定しているので、これは厳密な真値との誤差ではなく基準解との相対差である。

7｜実行前に確認すること

  1. 最初は各次数2〜3回に減らし、12枚のグラフが表示されるか確かめる。
  2. 各 n で100回に戻し、残差・相対誤差・計算時間の分布を記録する。
  3. 消去法の計算時間には、行列生成・基準解・残差計算を混ぜない。
  4. 800次が長すぎる場合は、消去法の行更新をNumPyの配列演算へ移す。その際も部分ピボット選択と後退代入を自分の実装として保持する。

別ファイル kadai1_0.py にある n[i] は、i が100などの行列サイズなので添字として使えない。for n in [100, 200, 400, 800]: として、そのまま make_square_matrix(n) に渡す。
