# 解説資料を書く

コードを**初めて読む人**が、他の資料を開かずに読み切れる解説を書く。
この skill は特定のリポジトリに依存しない。**出力先は毎回ユーザーに確認する**（§0）。

この skill の存在理由は、**読者が答え合わせしながら読めること**である。
「〜になっています」という要約で済ませた時点で資料の目的は崩れる。実物を貼る。

## 引数

`$ARGUMENTS` で以下を指定可能（フラグ形式・自然言語どちらも対応）:

| オプション | 説明 | 例 |
| --- | --- | --- |
| （無印） | 解説対象のファイル・ディレクトリ・テーマ | `/explain src/utils/csv.ts` / 「CSV出力について」 |
| `-o, --out` | 出力先ディレクトリ。**未指定なら必ず聞く**（既定値は持たない） | `-o docs/catch-up` |
| `-n, --number` | 先頭の連番・枝番を指定 | `-n 14` / `-n 05_2` |
| `--max-lines` | 1 ファイルの上限行数（既定 300） | `--max-lines 250` |
| `--single` | 分冊せず 1 ファイルで書く（短いテーマ限定） | 「1枚にまとめて」 |
| `--no-quiz` | 理解度チェックを付けない | 「クイズは要らない」 |
| `--level` | 読者の想定（既定 `zero` = プログラミング未経験） | `--level dev`（開発者向け・たとえ話を減らす） |
| `--update` | 既存資料をコードの現状に合わせて更新する | `/explain --update 13_4` |

## 使用例

```
/explain src/services/export.py
/explain -o docs/catch-up 用語辞書の近似表記チェックについて資料を作って
/explain -n 14 --max-lines 250 worker の非同期処理
/explain --update 13_4    # 行番号と引用を現在のコードに合わせ直す
/explain --single --level dev このPRで何が変わったかの説明資料
```

## 実行手順

### 0. 出力先を確定する（必ず最初に）

出力先はプロジェクトごとに違うので、**この skill は既定の出力先を持たない**。

1. `-o` / `--out` が渡されていれば、それをそのまま使う（聞き返さない）。
2. 渡されていなければ、**書き始める前に必ずユーザーに聞く**。AskUserQuestion が使えるならそれで聞く。
   聞くときは、リポジトリを見て見つけた候補を選択肢にする:

   ```bash
   # 既存の資料置き場を探す
   ls -d docs 2>/dev/null
   find . -maxdepth 3 -type d \( -name docs -o -name doc -o -name catch-up -o -name handbook \) \
     -not -path '*/node_modules/*' -not -path '*/.git/*' 2>/dev/null
   ```

   - 既存の解説資料ディレクトリが見つかったら、それを第一候補にする（既存の連番・命名に合わせられる）
   - 見つからなければ `docs/catch-up/` を提案候補として出す。ただし**勝手に決めない**
3. 確定した出力先を、以降この資料群の `<出力先>` として一貫して使う。
   本文中の相対リンク・目次・検算コマンドはすべてこのディレクトリ基準にする。
4. 出力先に**既存の資料があるか**を確認し、あれば連番・ファイル名の付け方・体裁をそれに合わせる。

   ```bash
   ls <出力先>
   ```

### 1. 対象と読者を確定する

対象が曖昧なとき（「あの処理」等）だけ聞き返す。それ以外は聞かずに進める。
確定したら**対象コミットを記録する**:

```bash
git rev-parse --short HEAD 2>/dev/null || date +%Y-%m-%d
```

git 管理下でないリポジトリなら、コミットの代わりに**日付**を記録する。
行番号はこの時点のものとして資料に明記する。

### 2. 実コードを全部読む

解説するファイルは**全文読む**。呼び出し元・呼び出し先・型の定義場所・テストまで辿る。
読まずに書いた説明は必ずずれるので、推測で埋めない。

対象範囲が広くて読み切れないときだけ Explore エージェントに調査させる。
ただし**引用するコードは自分で読んだ実物**に限る。

### 3. 構成を先に設計する（書き始める前）

節の区切りを、1 ファイル 200〜300 行に収まるよう**先に**割り付ける。
書き上げてから切るのではなく、切る前提で設計する。

- 分冊の命名は既存の枝番の後ろにもう 1 段足す（`05_1_0` `05_1_1` … `05_1_6`）
- `_0` は目次ページ。本文は書かない
- 節番号（`## 0.` 〜）は**分冊をまたいで通し**にする
- ページ数の目安: 5 本を超えるなら分割の粒度が細かすぎないか、10 本を超えるならテーマを割れないか見直す

設計が終わったらユーザーに**分冊一覧（ファイル名・内容・目安時間）だけ先に提示**し、承認を得てから本文を書く。
20 ページ分書いてから構成をやり直すのが最大の無駄である。

### 4. 各ページを書く

体裁は `references/page-template.md` に従う。必須要素は以下。

| 要素 | 場所 | 内容 |
| --- | --- | --- |
| 見出し | 1 行目 | `# NN_M. テーマ — このページの主題` |
| ナビ | 見出し直後と末尾 | `← 目次` / `← 前` / `次 →` のリンク |
| 前提ブロック | 冒頭 `>` 引用 | このページで分かること・対象コミット（または日付）・前に読むとラクなページ |
| 目安時間 | 目次ページの表 | 計算式は下記 |
| 実コード引用 | 各節 | `// path/to/file.ts:87` のコメント付きで**実物をそのまま**貼る |
| 図 | 節ごとに 1 枚以上 | mermaid と AA の使い分けは下記 |
| 理解度チェック | 末尾 | 3 問。`--no-quiz` 指定時は省略 |
| 次にどこを読むか | 末尾 | 「知りたいこと → 行き先」の表 |

引用のパスは**リポジトリルートからの相対パス**で書く（検算スクリプトがこの形式で実在確認する）。

### 5. 全体目次を更新する

`<出力先>/00_*.md` の「分冊について」「ファイルの一覧」の表に追記する。
全体目次がまだ無ければ `<出力先>/00_はじめに-読む順番.md` として新規作成し、
そこに「この資料群の読む順番」「ファイルの一覧（目安時間つき）」を置く。
新しい分冊を足したのに 00 を更新しないと、誰にも見つけてもらえない。

### 6. 検算する

```bash
bash .claude/skills/explain/scripts/check_docs.sh <出力先>
```

行数超過・リンク切れ・存在しないファイルへのコード引用・行番号の範囲外を検出する。
**赤が出たまま完了報告をしない。**

## 守るルール

### 前提知識ゼロで読める（最重要）

1. **登場する型・関数は、どのファイルに定義があるかを必ず書く。**
   「`Document` を受け取る」だけでは不十分。どのファイルに定義があるか、
   解説対象のフォルダを探しても出てこないこと、まで書く。

2. **言語の記法・デコレータ・標準ライブラリは、その場で説明する。**
   `@cached_property` `@dataclass` `(?<=...)` `import type` `() =>` のような、
   知っている人ほど飛ばすものを飛ばさない。「付けない場合／付けた場合」の比較か、
   「無いと何が起きるか」の具体例を添える。

3. **むずかしい言葉には、その場でたとえ話をつける。**
   ただし `--level dev` のときはたとえ話を減らし、設計判断の理由に紙面を回す。

4. **他ページを開かないと読めない資料にしない。** 参照はリンクで示しつつ、
   必要な用語はその分冊の中で説明し直す。

### 実コードで解説する

- 引用は**実物のコピー**。手で打ち直さない。省略箇所は `...` と書く
- 先頭行に `# src/pipeline.py:240` の形で、リポジトリルートからの相対パスと行番号を書く
- 「〜になっています」で済ませない。該当行を貼ってから説明する
- 落とし穴・仕様の罠（「画面で絞り込んでも出力は全件」等）を見つけたら必ず書く。
  読者が「バグでは？」と思う場所こそ資料の価値が出る

### 図

| 描くもの | 使うもの |
| --- | --- |
| 流れ・分岐・依存関係・読む順番 | mermaid（`flowchart LR` / `TB` / `sequenceDiagram`） |
| データの変形過程、2 つの実装の対比、メモリ上の様子、処理の番号付き手順 | AA（コードブロック内の罫線図） |

mermaid のラベルは `A["日本語ラベル"]` と**必ずダブルクォートで囲む**（囲まないと括弧や `/` で描画が壊れる）。

### 目安時間

`目安（分） = 本文の文字数 ÷ 500`（コードブロック内は 1/2 で数える）。切り上げて分単位。
目次ページの表と、複数ページの合計を「コース」として 00 に書く。

### 理解度チェック

各ページ末尾に 3 問。暗記を問わない。**「触るならどこか」「片方だけ直すと何が壊れるか」を問う。**

```markdown
## 理解度チェック

<details>
<summary><b>Q1.</b> CSV に列を 1 つ足したい。直すファイルは何個？</summary>

**A.** 最低 2 個（フロント側の整形とバックエンド側の書き出しが写しの関係）。
片方だけ直すと再現性の検証が静かにずれる。→ §8.2
</details>
```

- 答えは `<details>` で畳む。本文の節番号へのリンクを必ず付ける
- 1 問目は「このページの一番の山場」、3 問目は「知らないとハマる落とし穴」から作る

### 分冊

- 1 ファイル 200〜300 行。超えたら**内容を削るのではなく分ける**
- `_0` 目次ページに置くもの: 扱うファイルの一覧（主役／脇役）・全体の流れの図・分冊一覧の表（目安時間つき）
- 各分冊の先頭と末尾に `← 前 ／ 次 →`、先頭に `← 目次`

## 注意事項

- 古い設計書と食い違ったら**コードのほうが正しい**。食い違いを見つけたら資料にその旨を書く
- 使われていないフォルダ・死んだコードに気づいたら「今は使われていない」と明記する
- 更新（`--update`）のときは対象コミットの行を書き換え、引用と行番号を全部取り直す
- 資料を書いている最中にコードのバグを見つけても**直さない**。資料に書いて報告する
