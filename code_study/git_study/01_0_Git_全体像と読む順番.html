この資料のゴールは、git pull が失敗したときに .git の中を見て原因を特定できる状態です。

いちばん先に知っておくこと：.git は 4 つのものしか持っていない

① 中身objects/不変・追記のみce/013625…

ファイル名＝中身の SHA-1。blob / tree / commit / tag が入る

② 名札refs/可変・41 バイトrefs/heads/main

40 桁のハッシュ + 改行。ブランチを切る＝このファイルを 1 個作る

③ 今どこHEAD21 バイト・1 行ref: refs/heads/main

② のどれを指すかを書いた転送指示

④ 下書きindexバイナリ・1 個だけ(binary)

作業ツリーと objects の間に挟まる中間状態

refs/ 自体はただのディレクトリで、中身を持っているのはその下のファイルです。HEAD は refs/ の中ではなく .git 直下にあり、形式も 40 桁ハッシュではありません。（config や hooks/ もありますが、これらは設定と拡張ポイントであって履歴データではないので別枠です。§2.2 で扱います。）

この 4 つの区別が付けば、あとは全部この上に乗っています。

コマンド① objects② refs③ HEAD④ index作業ツリー
git add書き足す——書き換える—
git commit書き足す③ が指すものを進める———
git branch x—1 個増やすだけ———
git switch x——書き換える合わせる合わせる
git fetch書き足すrefs/remotes/ 以下だけ———
git merge / pull書き足す③ が指すものを進める—合わせる合わせる

① objects/ の中身 — 入っているのは 4 種類だけ

「ファイルもディレクトリもコミットも全部ここ」と書いたので、先に中身の地図を出します。実バイト列・ハッシュの手計算・落とし穴は §1 でやるので、ここでは種類と役割分担だけ掴んでください。

種類対応するもの持っている情報持っていない情報
blobファイルの中身バイト列だけファイル名・更新日時・置き場所
treeディレクトリ 1 段分「モード + 名前 + 子のハッシュ」の並び中身そのもの（blob のハッシュを指すだけ）
commitある時点のスナップショット 1 個根の tree 1 個 + 親コミット + 作者 + 日時 + メッセージ差分（どのファイルを変えたか）
tag注釈付きタグ（git tag -a）指す先 + タグ名 + 署名者 + メッセージ—

git log も git diff も git checkout も、この 4 種類を読んで表示を組み立てているだけです。

実物：hello.txt 1 個を 1 回コミットすると 3 個できる

$ find .git/objects -type f
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a   ← blob   （hello.txt の中身）
.git/objects/aa/a96ced2d9a1c8e72c56b253a0e2fe78393feb7   ← tree   （リポジトリ直下の一覧）
.git/objects/ae/f822d7070fcc3133b890df8beee1272a784c9b   ← commit （上の tree を指す）

ここで効いてくるのが役割分担です。

  • blob は名前を知りません。「hello.txt」という名前を持っているのは tree のほうです。だから中身が同じファイルが 2 つあっても blob は 1 個で済み、リネームは blob を増やしません。
  • commit は差分を知りません。持っているのは「そのときの全体像（根の tree）」と「親」だけです。git show が差分を出せるのは、親の tree と自分の tree をその場で比較しているからです。
  • tree は入れ子になります。src/api/main.py を 1 文字直すと、blob 1 個に加えてapi → src → 根 の tree が全部作り直されます（= 小さな変更でも objects は数個増える）。

どのオブジェクトも同じ形式で保存されている

blob の部分が tree / commit / tag に変わるだけで、4 種類とも同じ形です。zlib 圧縮されているので cat では読めず、覗くには git cat-file（§0.2）を使います。

$ git cat-file -t ce013625   # 種類
blob
$ git cat-file -p ce013625   # 中身
hello

そして「ファイル名 = 中身の SHA-1」という命名こそが、①を不変にしている仕掛けです。次の節で見ます。

なぜ「ファイル名 = 中身の SHA-1」だと書き換わらないのか

①の objects/ だけ「不変」と書いたので、先にここを説明します。Git のほぼ全部の性質がここから出ます。

ハッシュは「中身から計算した値」であって、Git が採番したものではない

hello\n を保存すると ce013625... という名前のファイルができます。これは空き番号ではなく中身を SHA-1 に通した結果で、手で計算しても一致します。

$ printf 'blob 6\0hello\n' | shasum
ce013625030ba8dba906f756967f9e9ca394464a  -

だから「中身を変える」と、名前と中身が矛盾する

ce013625... の中身を hello から bye に書き換えたとします。

   ファイル名:  ce013625...  ＝「中身が hello\n であるもの」の意味  ／  実際の中身: bye  ← 食い違う

Git は読むときに中身をハッシュにかけ直せるので、これは破損として検出されます。実際に壊してみます。まずオブジェクトファイルは読み取り専用で作られています。

$ ls -l .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
-r--r--r--@ 1 akito_inoue  wheel  21 Sep 17 16:12 .git/objects/ce/0136...

chmod u+w して中身を bye\n に差し替えてから git fsck を走らせます。

$ git fsck
error: b023018cabc396e7692c70bbf5784a93d3f738ab: hash-path mismatch, found at: .git/objects/ce/0136...
missing blob ce013625030ba8dba906f756967f9e9ca394464a

「中身から計算すると b023018... なのに ce013625... の場所にある」と怒られ、本来あるはずの ce013625... は missing blob（行方不明）扱いになります。つまり「同じ名前のまま中身を差し替える」はルール上そもそも成立せず、Git にとって "変更" は常に「別の名前で新しいファイルを作る」ことになります。

元のまま残るce013625…"hello\n"
hello → bye に直すと
▶
新しく増えるb023018…"bye\n"

この性質から出てくる帰結

見かけの操作実際に起きていること
コミットメッセージを直す（--amend）別のコミットを新規作成し ② を向け直す。元のコミットは残る
rebase で履歴を作り直す全コミットを別ハッシュで作り直す。元も残る
ブランチを消す② のファイルを 1 個消すだけ。① には手を付けない
「間違えて消した」ほぼ必ず ① に残っている。名前（②）が外れただけ

.git/objects は追記専用のログです。削除が起きるのは git gc（§9.5）のときだけで、しかも「どの ref からも到達できない」かつ「一定期間が過ぎた」ものに限られます。復旧手順（§9.2）がほぼ全部「ハッシュを探して名前を付け直す」の形なのは、この不変性が前提にあるからです。本当に失われるのは、一度も git add していない内容だけです。

0.1この資料の実験を手元で再現する

全ページの出力は、以下の手順で作った 3 つのリポジトリから採取しています。写経すると理解が一段深くなるので、余裕があればやってみてください。

mkdir -p ~/gitlab && cd ~/gitlab
git init --bare server.git                  # 中央リポジトリ（GitHub の代わり）

mkdir myapp && cd myapp                     # 自分の作業リポジトリ
git init
printf 'hello\n' > hello.txt
git add hello.txt && git commit -m "最初のコミット"
git remote add origin ../server.git
git push -u origin main

cd ~/gitlab && git clone server.git bob     # 同僚の作業リポジトリ

以降、myapp を「自分」、bob を「同僚」、server.git を「GitHub 上のリポジトリ」として読んでください。ハッシュ値は必ずずれます（コミットに作者名と時刻が入るため。理由は §1.5）。ハッシュそのものではなく、どのファイルがどう変わったかを見てください。

0.2この資料でよく使う「中身を覗く」コマンド

.git/objects の中は zlib 圧縮されていて cat では読めません。読むための道具が要ります。

コマンド何が見えるか
git cat-file -t / -p / -s <hash>オブジェクトの種類 / 中身 / バイト数
git ls-files -s / -u.git/index の中身 / 未解決（コンフリクト）だけ
git rev-parse <名前>名前 → 40 桁ハッシュの変換
git reflog.git/logs/HEAD を読みやすくしたもの

cat-file は「.git/objects 専用の cat」だと思えば十分です。一覧は 01_9 §9.6 に。

理解度チェック

Q1. git branch feature を実行したとき、.git/objects/ にファイルは何個増える？

A. 0 個。.git/refs/heads/feature という 41 バイトのテキストが 1 個増えるだけで、オブジェクトは 1 バイトも増えない。Git のブランチが「軽い」と言われる理由はこれ。 → §5.1

Q2. git fetch したのに git log の先頭が変わらない。バグ？

A. 仕様どおり。fetch が動かすのは refs/remotes/origin/main だけで、refs/heads/main（= git log が見ている場所）には触らない。 → §7.2

Q3. 同じ手順を 2 回やると、コミットのハッシュは同じになる？

A. ならない。コミットオブジェクトに committer ... 1789606800 +0900 という時刻が含まれるため。逆に blob（ファイル内容）は中身が同じなら必ず同じハッシュになる。 → §1.5

Q4. ファイル 1 個だけのリポジトリで最初のコミットをすると、.git/objects/ は何個増える？

A. 3 個（blob 1 + tree 1 + commit 1）。「ファイル 1 個 = オブジェクト 1 個」ではない。深い階層だと、その階層数ぶん tree が増える。 → §1.2 §1.4
