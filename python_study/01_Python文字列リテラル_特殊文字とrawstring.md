## 0. 結論を先に

`AtCoder/src/abc476_b.py` で `*` を文字として扱うために `r"*"` と書きましたが、
**`r"*"` と `"*"` と `'*'` は完全に同じ 1 文字の文字列**です。`r` は要りませんでした。

```
>>> "*" == r"*"
True
>>> len("*"), len(r"*")
(1, 1)
```

苦労した原因は、おそらく次の取り違えです。

```
  ❌ 思っていたこと : 「* は Python にとって特別な文字だから、そのまま書くと壊れる」
  ⭕ 実際           : 「* が特別なのは "正規表現" という別の層。文字列リテラルでは何でもない」
```

Python の文字列リテラルで特別扱いされるのは、**バックスラッシュ `\` と、囲んでいるクォート**の
2 つだけです（f-string の `{}` だけが例外 → §6）。`*` `?` `.` `+` `[` `^` `$` `|` `(` は
すべて**ただの記号**で、そのまま書けばそのまま入ります。

### 「層」で考える

同じソースコードが、どこで何に化けるかを追ってください。

```
  ソースに書いた形      Python の構文解析          メモリ上の文字列        それを渡す先
  ───────────────      ──────────────────         ────────────────       ────────────────
   "a\tb"        ──→   \t をタブ1文字に変換  ──→   a<TAB>b  (3文字)  ──→  ==      : ただの比較
   r"a\tb"       ──→   何も変換しない        ──→   a \ t b  (4文字)  ──→  print   : ただの表示
   "*"           ──→   変換するものが無い    ──→   *        (1文字)  ──→  re.match: ★ここで
   r"*"          ──→   変換するものが無い    ──→   *        (1文字)                 初めて特別
                        ↑ 左半分＝§1〜§6                                  ↑ 右半分＝§7
```

**左半分（リテラルの解釈）と右半分（渡した先での解釈）は別の話**です。

## 1. ソースの「書き方」と、メモリ上の「中身」は別物

文字列リテラルとは**ソースコードに書く記法**のことで、書いた通りの文字が入るとは限りません。
確かめる道具は次の 4 つです。

| 道具 | 何をするか |
|---|---|
| `len(s)` | **中身**の文字数。書いた記号の数ではない |
| `repr(s)` | リテラル記法に**戻した**表示。REPL が勝手に使うのもこれ |
| `ascii(s)` | `repr` と同じだが、日本語や絵文字も `\u3042` の形にする |
| `print(s)` | 中身をそのまま表示。タブが空白に見えるので調査には不向き |

```
>>> s = "a\tb"
>>> len(s)
3
>>> repr(s)
"'a\\tb'"
```

ソースには `a \ t b` の 4 文字を書いたのに中身は 3 文字です。`\t` の 2 文字が、
タブという 1 文字に**変換されて**います。

> **`repr()` の表示がややこしい理由。** `repr(s)` は「この中身を作るリテラル」を返すので、
> `\` 1 個を表すのに `\\` と 2 個書きます。**`\\` と見えたら中身は `\` 1 個**と読み替えてください。
> 困ったら `len()` で数えるのが確実です。

## 2. 特別なのは「`\`」と「囲みクォート」だけ

### 2.1 バックスラッシュ — エスケープシーケンス一覧

`\` の次の 1 文字（または数文字）は、まとめて別の文字に変換されます。

| 書き方 | 中身 | 優先度 |
|---|---|---|
| `\n` / `\t` | 改行 / タブ | ★★★ |
| `\\` | バックスラッシュ 1 個 | ★★★ |
| `\'` `\"` | クォートそのもの（§2.2） | ★★★ |
| 行末の `\` | **その改行を無かったことにする**（行継続） | ★★ |
| `\r` | 復帰（CRLF 改行の前半） | ★★ |
| `\xHH` | 16 進 2 桁のコードの文字。`\x41` → `A` | ★★ |
| `\uXXXX` / `\UXXXXXXXX` | Unicode コードポイント。`\u3042` → `あ` | ★★ |
| `\N{名前}` | Unicode 名。`\N{GREEK SMALL LETTER ALPHA}` → `α` | ★ |
| `\0` / `\OOO` | ヌル文字 / 8 進数（`\101` → `A`）。混乱のもとなので使わない | ☆ |
| `\a` `\b` `\f` `\v` | ベル・バックスペース・改ページ・垂直タブ。ほぼ使わない | ☆ |

```
>>> "\x41", "\101", "\u3042", "\U0001F600"
('A', 'A', 'あ', '😀')
```

### 2.2 囲みクォート — 同じ記号が出てきたら閉じてしまう

`"` で囲んだ中に `"` が出ると、そこで文字列が終わったと解釈されます。逃げ道は 3 つ。

```
>>> "he said \"hi\""     # ① \ でエスケープする
'he said "hi"'
>>> 'he said "hi"'       # ② 囲みを ' に変える  ← いちばんラク
'he said "hi"'
>>> """he said "hi" """  # ③ 三重クォートで囲む（中に改行もそのまま書ける）
'he said "hi" '
```

**Python では `'` と `"` に機能の差はありません。** シェルや PHP と違い、`'` の中でも
`\n` は改行になります。どちらを使うかは好みだけの問題です。

### 2.3 だから `*` は何もしなくていい

```
>>> len("*"), "*" == "\u002a"
(1, True)
>>> "a*b".split("*")
['a', 'b']
>>> "ab*c".replace("*", "-")
'ab-c'
```

`split` も `replace` も `==` も `in` も**正規表現ではありません**。渡した文字列を
1 文字ずつそのまま比べるだけなので、`*` を逃がす必要はありません。

## 3. 落とし穴 —「知らないエスケープ」は黙って生き残る

もし `*` を逃がそうとして `"\*"` と書いていたら、もっと厄介でした。

```
>>> s = "\*"
>>> len(s), s == "*"
(2, False)
```

**`\*` は `*` になりません。** Python は知らないエスケープを**そのまま 2 文字として残す**ためです。
同じことは `"\d"` `"\w"` `"\s"` でも起きます。

```bash
$ python3 -W always -c "print(repr('\d'))"
<string>:1: DeprecationWarning: invalid escape sequence \d
'\\d'
```

| Python | 挙動 |
|---|---|
| 〜3.11（手元の 3.9.6 もここ） | `DeprecationWarning`。**既定では表示されない**ので気づけない |
| 3.12〜 | `SyntaxWarning`。既定で表示される |
| 将来 | `SyntaxError` にする予定が公式に告知されている |

`"\*"` は「今は偶然 2 文字で残っていて、警告も出ず、いつか構文エラーになる」書き方です。
**`\` は意味があるときだけ書く**と決めてください。

## 4. `r` プレフィックス（raw string）が実際にやっていること

`r` を付けると、**`\` のエスケープ変換だけを止めます**。それ以外は何も変わりません。

```
>>> len("\t"), len(r"\t")
(1, 2)
```

```
  "C:\new\table"   →  C:<改行>ew<タブ>able     ← \n と \t が変換されてしまう
  r"C:\new\table"  →  C:\new\table             ← 書いた通り
```

`r` が効くのは**中身に `\` を入れたいとき**だけです（正規表現 §7.2 / Windows のパス / LaTeX）。
`r"*"` のように **`\` を 1 個も含まない文字列に `r` を付けても何も起きません**。
害もありませんが、読む人に「ここに `\` の罠があるのか」と一瞬考えさせるぶん損です。

### 4.1 raw string の落とし穴 2 つ

**① 末尾を `\` で終われない。**

```bash
$ python3 -c "print(r'\')"
SyntaxError: EOL while scanning string literal
```

`r` を付けても、**クォートを閉じる判定のときだけは `\` が効いてしまう**ためです。
`r"C:\path\"` は書けません。`"C:\\path\\"` か `r"C:\path" + "\\"` にします。

**② `\'` はクォートを逃がすが、`\` も中身に残る。**

```
>>> r'a\'b'
"a\\'b"
>>> len(r'a\'b')
4
```

`a`, `\`, `'`, `b` の 4 文字です。「エスケープが効かない」のではなく
「**効くけれど `\` を食べない**」が正確な理解です。

## 5. プレフィックス一覧

クォートの直前に付けられる記号は 4 種類。大文字小文字はどちらでもかまいません。

| 前置き | 名前 | 何が変わるか | 型 |
|---|---|---|---|
| なし | 普通の文字列 | — | `str` |
| `r` | raw | `\` を変換しない（§4） | `str` |
| `f` | f-string | `{ }` の中を式として評価する（§6） | `str` |
| `b` | bytes | 文字ではなく**バイト列**。ASCII しか書けない | `bytes` |
| `u` | 旧 unicode | **何もしない**。Python 2 との互換で残っているだけ | `str` |

組み合わせは `rb` / `br` / `rf` / `fr` が使えます（順序はどちらでも可）。
**`bf` は存在しません**（f-string は `str` 専用）。`u` は他と組み合わせられません。

```
>>> rb"\n"
b'\\n'
>>> b"\d"        # bytes でも「未知のエスケープ」は同じく残る（§3）
b'\\d'
```

競技プログラミングで `b` を使うことはまずありません。`f` と `r` だけ覚えれば十分です。

## 6. f-string の `{}` は「リテラルの中のもう 1 つの層」

`f` を付けたときだけ **`{` と `}` が特別**になります。§2 の唯一の例外です。

```
>>> x = 1
>>> f"{x} {x!r} {x=} {{波括弧}}"
'1 1 x=1 {波括弧}'
```

| 書き方 | 意味 |
|---|---|
| `{式}` | 式を評価して埋め込む |
| `{{` `}}` | `{` `}` そのもの（**`\{` ではない**） |
| `{x!r}` | `repr(x)` を埋める |
| `{x=}` | `x=1` のように**変数名ごと**出す（3.8〜）。print デバッグ用 |
| `{x:.3f}` `{x:>8}` | 書式指定（小数 3 桁・右詰め 8 幅） |

### 6.1 バージョンで変わる 2 つの制限

手元の 3.9.6 では次の 2 つがエラーです。**どちらも Python 3.12 で解禁されました**。

```bash
$ python3 -c "print(f'{\"a\n\"}')"
SyntaxError: f-string expression part cannot include a backslash

$ python3 -c "d={'k':1}; print(f'{d['k']}')"
SyntaxError: f-string: unmatched '['       ← 外と同じクォートを内側で使えない
```

3.11 以前では、**`{}` の中のクォートは外側と別のものにする**、**`{}` の中に `\` を書かない**
（変数に出しておく）が回避策です。AtCoder のジャッジは 3.11 系のことが多いので、
古い側に合わせるのが安全です。

## 7. `*` が本当に「特別」になる場所

リテラルを抜けたあと、**渡した先のライブラリ**が改めて文字列を解釈することがあります。

| 渡す先 | `*` の意味 | 1 文字の `*` として扱うには |
|---|---|---|
| `==` `in` `.split()` `.replace()` `.count()` | **意味なし。ただの記号** | 何もしない ← 今回のケース |
| `re`（正規表現） | 直前の要素の 0 回以上の繰り返し | `\*` と書く / `re.escape("*")` |
| `glob` / `fnmatch` | 任意の文字列にマッチ | `[*]` と書く |
| f-string / `str.format` | 意味なし（特別なのは `{}`） | 何もしない |
| `%` 書式 | 幅の指定に使える（`"%*d" % (5, 42)`） | `%` 自体を出すのは `%%` |
| シェル（`shell=True` 等） | ファイル名展開 | クォートで囲む / `shell=True` を避ける |

```
>>> import re
>>> re.fullmatch("a*b", "aaab")               # * は「a の繰り返し」
<re.Match object; span=(0, 4), match='aaab'>
>>> re.fullmatch(re.escape("a*b"), "a*b")     # escape すると * は文字そのもの
<re.Match object; span=(0, 3), match='a*b'>
```

### 7.1 なぜ正規表現には `r""` を付けるのか

正規表現で「数字」を表す記号は `\d` です。普通の文字列で書くと **`\` が 2 回解釈される**
危険があります。

```
  ソース          リテラル解釈後       re が受け取るもの
  ──────          ─────────────       ─────────────────
  r"\d"    ──→    \ d （2文字）  ──→   \d = 数字 ⭕
   "\d"    ──→    \ d （2文字）  ──→   \d = 数字 ⭕ だが DeprecationWarning（§3）
   "\\d"   ──→    \ d （2文字）  ──→   \d = 数字 ⭕ ただし読みにくい
   "\b"    ──→    バックスペース ──→   別物 ❌ 正規表現の \b（単語境界）にならない
```

`"\d"` が**たまたま動いてしまう**のが厄介なところです。`\b` `\n` `\t` のように
Python 側にも意味がある記号だと静かに壊れます。**正規表現は必ず `r""`** と機械的に決めるのが正解。
逆に言えば、**正規表現を使っていないなら `r""` は要りません**。これが今回の話です。

## 8. 自分のコードを読み直す

```python
# AtCoder/src/abc476_b.py:1
# https://atcoder.jp/contests/abc476/tasks/abc476_b

N = int(input())
S = input()
T = input()

match = True

for i in range(N):
    if S[i] == T[i] or T[i] == r"*":
        continue
    else:
        match = False

if match:
    print("Yes")
else:
    print("No")
```

`T` の `*` を**ワイルドカードとして解釈しているのは、自分で書いた `if` 文**であって、
Python でも `re` でもありません。だから逃がす必要は最初からありませんでした。

```python
# AtCoder/src/abc476_b.py:10
    if S[i] == T[i] or T[i] == r"*":
```

この行の `r"*"` は `"*"` に置き換えられます。**動作は 1 ビットも変わりません。**

### 8.1 ついでに気になる 2 点（バグではありません）

| 箇所 | 気になること | どうするか |
|---|---|---|
| `AtCoder/src/abc476_b.py:13` | 不一致が確定しても最後までループが回る | `match = False` の直後に `break` |
| `AtCoder/src/abc476_b.py:15` | `if match:` の後ろに**空白が 1 つ**残っている | 実害なし。エディタ設定で消せる |

`input()` を使っているので改行は取り除かれています。`sys.stdin.readline` に替えるときは
`.rstrip()` が必須です（→ [01_8 Python落とし穴](../AtCoder/docs/01_8_Python落とし穴と提出前チェックリスト.md) §8.1）。

### 8.2 もし `re` で書くなら（比較用）

正規表現で「任意の 1 文字」は `*` ではなく `.` です。だから `*` を**変換する**必要があります。

```python
import re
pattern = "".join("." if c == "*" else re.escape(c) for c in T)
print("Yes" if re.fullmatch(pattern, S) else "No")
```

`re.escape(c)` が要るのは、`T` に `.` や `+` が含まれていたときに**そちらが特別扱いされない
ようにするため**です。素朴に書くほうが短くて速いので、競プロでは元のコードのままで正解です。

## 9. 迷ったときの決定表とデバッグ手順

| やりたいこと | 書き方 |
|---|---|
| `*` `?` `.` `+` などの記号を 1 文字として使う | `"*"` そのまま。**`r` も `\` も不要** |
| 文字列に `\` を入れたい | `r"..."` または `"\\"` |
| 文字列に `"` を入れたい | 囲みを `'...'` にする |
| 改行・タブを入れたい | `"\n"` `"\t"`（**`r` を付けたら変換されない**） |
| 正規表現を書く | 必ず `r"..."` |
| 変数を埋め込む | `f"..."`。`{` 自体は `{{` |
| 正規表現で記号を文字として扱う | `re.escape(s)` |

思った文字列になっているか怪しいときは、この順で確認します。

```
  1. len(s)    … 文字数は想定通りか（\t が 2 文字になっていないか）
  2. repr(s)   … \\ と見えたら中身は \ 1 個
  3. ascii(s)  … 全角空白・BOM・見えない文字を炙り出す
  4. list(s)   … 1 文字ずつバラして目視
```

```
>>> s = "\*"
>>> len(s), list(s)
(2, ['\\', '*'])
```

## 理解度チェック

<details>
<summary><b>Q1.</b> <code>"*" == r"*"</code> は True か False か。理由も。</summary>

**A.** **True**。`r` は `\` のエスケープ変換を止めるだけで、`\` を含まない文字列には何の影響もない。
両方とも中身は `*` 1 文字。→ §0 / §4
</details>

<details>
<summary><b>Q2.</b> <code>s = "\*"</code> と書いたとき <code>len(s)</code> はいくつか。
なぜ「そのうち壊れる書き方」なのか。</summary>

**A.** **2**（`\` と `*`）。Python は知らないエスケープを 2 文字のまま残すので `s == "*"` は False。
3.11 以前は既定で表示されない `DeprecationWarning`、3.12 以降は `SyntaxWarning`、
将来は `SyntaxError` にすると告知されている。→ §3
</details>

<details>
<summary><b>Q3.</b> <code>re.findall("\d+", s)</code> は今のところ正しく動く。
それでも <code>r"\d+"</code> と書くべき理由は？</summary>

**A.** `\d` は Python が知らないエスケープなので、偶然そのまま残って動いているだけ。
同じ書き方でも `"\b"` `"\n"` のように**Python 側にも意味がある記号だと静かに別物になる**。
どれが安全か覚えるより、正規表現は必ず `r""` と決めるほうが事故らない。→ §7.1
</details>
