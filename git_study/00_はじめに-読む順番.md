この資料群は、**Git を `.git` フォルダの中身から理解する**ための解説です。
「コマンドの使い方」ではなく「そのコマンドが `.git` のどのファイルを書き換えたか」を追います。

検証環境: **git 2.50.1 (Apple Git-155) / macOS**。対象日: **2026-09-17**。
貼ってあるコマンド出力・ファイル内容は、すべて**実際に手を動かして採取した実物**です。

---

## なぜ `.git` から入るのか

Git のコマンドは表面上ばらばらに見えますが、やっていることは全部同じです。

```
  ┌────────────────────────────────────────────────┐
  │  Git のコマンドがやること（例外なくこの2つだけ）        │
  │                                                │
  │   1. .git/objects/ に「中身」を書き足す             │
  │   2. .git/refs/ や .git/HEAD の「文字列」を書き換える  │
  └────────────────────────────────────────────────┘
```

`merge` も `rebase` も `pull` も、この 2 つの組み合わせです。
逆に言えば、**`.git` の中の数個のテキストファイルが読めれば、Git の挙動はほぼ全部説明がつきます**。

`git log` や `git status` の出力を眺めても腑に落ちないのは、それらが
「`.git` の中身を人間向けに加工した結果」だからです。この資料では加工前を見ます。

## 分冊について

1 ファイル 200〜300 行に収まるよう分けています。`01_0` のような `_0` は目次ページです。
節番号（§1 〜 §9）は**分冊をまたいで通し**です。文中で「§7.3 を見てください」とあるときは、
§7 を扱う分冊（= `01_7`）を開いてください。節と分冊の対応は
[01_0](./01_0_Git_全体像と読む順番.md) の表にあります。

## この資料の書き方のルール

- コマンド出力は**実物のコピー**。省略した部分には `...` と書いてあります
- `.git` の中のファイルを引用するときは `# .git/HEAD` のようにパスを先頭に書きます
- ハッシュ値は実験で出た実物です。**手元で再現すると必ず別の値になります**
  （コミットには時刻と名前が入るため。§1.5 参照）
- 出力中の長い絶対パスは `.../lab/myapp` のように前半を `...` で省略しています
